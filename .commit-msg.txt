hook: useHotkeys, window-scoped chords with a text-field guard (#627)

`useHotkeys({ chords: "ctrl+s,escape" })` declares keyboard shortcuts for
the window. The engine owns the mechanism: `KeyBindingRegistry` is a
bounded, allocation-free table with a documented matching rule, and
`InputRouter` already dispatches it after the focused node's handler and
only when the key event was not consumed. This lands the hook's half.

The hook takes no target ref, because a shortcut belongs to the window and
not to an element. The behavior parses the chord list once, registers each
chord into the router's one registry, and holds the ids it got, which is
what makes detach exact: an update removes the old set before registering
the new one, so a component that re-renders does not accumulate bindings.

The behavior registers a marker binding rather than a callback. A behavior
may not invoke a callback (behavior-hooks-v1.md section 8), so the input
path reports the fired id through `InputDispatchResult::accelerator_fired`
and the generated base turns that into the component's handler call.

`allowInTextInput` is implemented, not just declared: while the focused
node is a `TextInput` or `TextArea` the behavior registers nothing, because
a chord that fires there steals a key the user is typing. The registry has
no "except when" rule, so the behavior re-evaluates on each update, which a
field gaining focus already triggers.

The destructor removes the bindings, so a behavior destroyed without an
explicit detach cannot leave the window firing a shortcut for a component
that no longer exists.

Evidence: `hotkeys` (12 rules, including the chord parser, the exact
modifier match, the update replacing the set, and the text-field guard),
`hook_manifest` and `behavior_registry`. Spec:
`docs/specs/use-hotkeys-v1.md`.
