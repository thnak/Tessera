hook: useInteractiveRole, so a nested control knows it is nested (#635)

`useInteractiveRole(target, { interactive })` marks an element as the
interactive surface of a composite and reports whether that surface is
itself nested inside another one. It exists for one WCAG defect: a control
inside a control. A screen reader announces both, and a pointer press on
the inner one also triggers the outer one because the click bubbles.

The flag lives on the node (`Node::set_interactive_parent`), not in the
behavior, because the descendant that needs the answer is a different
component, possibly in a different module. The scene is the only thing they
share, so a descendant reads the flag by walking its ancestors
(`InteractiveRole::has_interactive_ancestor`). A behavior that kept the
flag privately could not answer the question the hook exists to answer.

The hook does not set `role`, `tabIndex` or an accessible name, and it does
not stop a click from bubbling: it reports the situation so a component can
avoid the nesting in the first place, which is the only fix that works for
assistive technology too.

`node.hpp` is a grandfathered over-limit header (652 lines against a 500
hard limit), and the source-size gate only lowers a baseline, never raises
one. The flag and its accessor are 10 lines, so the same change condenses
ten lines of older comment in that file to stay at the baseline rather than
grow it. That is the gate working as intended: the file cannot get worse.

Evidence: `interactive_role` (9 rules, including the descendant walk and
the nested-surface output), `hook_manifest` and `behavior_registry`. Spec:
`docs/specs/use-interactive-role-v1.md`.
