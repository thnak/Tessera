# Developer workflow and generated-code ownership

Status: applies from Big Step C (compiler vertical slice) onward; the merger prototype was delivered in Big Step A (see [AGENTS.md, Big Steps](../../AGENTS.md#big-steps-group-work-dont-micro-step)). V1 below means the first-release scope defined there.

This guide is the practical companion to [ADR-008](../../decisions/ADR-008-protected-regions-and-manifest.md) (protected regions and binding manifest). A protected region is a block of developer-written C++ between `[DEVELOPER_LOGIC_START: bind::<id>]` and `[DEVELOPER_LOGIC_END: bind::<id>]` markers; the merger is the tool that re-inserts those blocks into regenerated files. It defines who owns which bytes in a Tessera
project and how regeneration, bindings, and protected regions behave.

## 1. Ownership rule

| Area | Owner | Rule |
|---|---|---|
| Everything outside protected regions in `.g.h`/`.g.cpp` | Compiler | Never edit; it will be regenerated |
| Inside `[DEVELOPER_LOGIC_START: bind::<id>]` … `END` | Developer | Survives regeneration |
| `src/main.cpp` and other non-generated files | Developer | Never rewritten by the generator |
| `tessera.json` | Developer | Validated; CLI flags do not rewrite it |
| `generated/bindings.json` | Compiler | Generated; do not hand-edit |

Generated file header:

```cpp
// Generated by Tessera. Do not edit outside protected regions.
```

Protected region:

```cpp
// [DEVELOPER_LOGIC_START: bind::on_click]
void onClick() {
    count_ += 1;
}
// [DEVELOPER_LOGIC_END: bind::on_click]
```

The marker `id` is a stable binding identifier derived from the `// Note: bind::<id>`
annotation in JSX. It is not a line number or a random id.

## 2. What survives regeneration

- Developer body inside a region whose id exists in the new generated file: **preserved**.
- A region only in the new generated file: **fresh generated stub**.
- A region only in the existing file: **kept on disk**, with a warning that the binding was
  removed/renamed. The merger never silently deletes developer code.
- Duplicate ids, missing end markers, or mismatched ids: **hard error**.
- Line endings: preserved per file; the repository uses LF except for Visual Studio solution/project files (`.gitattributes`).
- Formatting: generated code is formatted with the pinned `clang-format` before merging, so
  marker placement is stable.

Idempotency is a tested invariant:

```text
merge(merge(g, e), e) == merge(g, e)
```

## 3. Adding a component (target workflow)

1. Create `ui/MyComponent.tsx`.
2. Use only allowed hooks: `useState`, `useEffect`, `useRef`, `useAnimatedValue` (V1).
3. Put `// Note: bind::<id>` next to logic that needs a stable C++ region.
4. Run `tessera generate`.
5. Implement developer logic only inside the generated region.
6. Run `tessera build` / tests.
7. Commit both the TSX and generated files (generated output is deterministic and reviewable).

Unsupported patterns are rejected loudly: custom hooks, context, suspense, dynamic component
types, and non-static conditionals/loops. Error boundaries (components that catch errors from their subtree and show a fallback) are supported for isolating
subtrees; do not use them as a catch-all to hide bugs. See
[`error-boundaries-v1.md`](../specs/error-boundaries-v1.md).

## 4. Regeneration

The first implemented generator is the codegen CLI (Big Step C):

```bash
# Regenerate into the build output directory, merging every existing developer region.
tessera_codegen --out build/generated --namespace demo ui/Screen.tsx

# Add --verbose to report each file as written or unchanged.
tessera_codegen --verbose --out build/generated --namespace demo ui/Screen.tsx

# CI gate: fail when the output directory is stale; writes nothing.
tessera_codegen --check --out build/generated --namespace demo ui/Screen.tsx

# Numeric automation ids (docs/specs/automation-ids-v1.md): when a tessera.json is found at --root
# or above the input, its `app.namespace` is the id salt and its directory the project root, so
# every component and node gets a componentId/uiId and the scene node carries it as its automation
# id, and `automation.manifest.json` (ids to names, paths and sources) is written next to the generated
# files. A tessera.json without a usable `app.namespace` is an error. --salt overrides it.
tessera_codegen --out build/generated --namespace demo ui/Screen.tsx
tessera_codegen --salt factory --root . --out build/generated --namespace demo ui/Screen.tsx

# See tools/codegen and samples/compiler-demo (Demo.tsx + the committed developer seed).
```

The CLI reads one or more `.tsx` files and runs the real front end (lexer/parser → Tier-1
analysis → lowering → IR validation → codegen) in one process; diagnostics are first-error-only
and carry `file:line:column`. Exit codes are **0** ok, **1** diagnostics or drift, **2**
usage/setup.

Regeneration is incremental per file: the freshly generated text is merged with the file already
in the output directory (`merge(generated, existing)`), and the file is rewritten only when the
merged bytes differ. A second run with unchanged inputs is a byte- and mtime-no-op, so build
systems do not rebuild. Files outside `--out` are never touched, and generated names are validated
(`component-name.hpp`/`.cpp`; no path separators). Files with regions that vanished produce merger
warnings; outside-region edits are drift for `--check` and are overwritten by `--write` (the rule
below).

The output directory is build output: keep it out of version control. Commit only the `.tsx`
sources and the developer files that the team owns (the sample's seed lives at
`tests/golden/codegen/demo/Demo.cpp` and the build regenerates over it).

A controlled `TextInput`/`TextArea` owns its generated `EditController`/`TextInputRuntime`; bind
input events through the scene (do not call a controller directly) so committed edits emit
`TextChange` and the generated `onChange` setter updates state and repaints. A `value` prop must
produce a printable text value; an `onChange` binding must take a `TextChangeEvent` payload.

Generated components expose three lifecycle entry points: `build(parent)` attaches the tree,
`apply_state()` recomputes interpolated text (paint-only dirty marks), and `update()` calls
`update_effects()` then `apply_state()`. A manual `update()` is no longer needed after state changes:
use the generated `set_<state>(value)` setters (they schedule the
component) and install an `UpdateScheduler` on the `FramePipeline`, which flushes it at the start of
each tick so effects run and interpolated text is written in that frame. Call setters on the UI
thread only (debug builds assert); from a worker, post a completion and set state in its callback.
Direct field assignment in a developer region still needs `schedule_update()` (or a manual
`update()` in a headless test). Developer effect
regions run inside `update_effects()`; mutate state cells there and `update()` refreshes the text
afterwards.

A component with a conditional child or a keyed list also gets generated child-set paths;
`apply_state()` runs them first. A conditional branch is built once and attached/detached at its
source position, so a child-set change marks the shared parent `Layout|Paint|Render` (never `Style`)
and an unchanged condition marks nothing. A keyed list has no item cap: its table
grows to the source, reuses nodes by key, and allocates nothing when the key list is unchanged. A list-typed state cell is authored like any other
state: `useState<string[]>(["a", "b"])` (literal elements) or a list reference; dynamic elements,
record element types and list-typed props are not available yet (see
[`compiler.md` §11](../design/compiler.md#11-c-codegen-first-slice-implemented)).

### 4.1 Generated-UI headless demo

`tests/integration/generated_ui_tests.cpp` runs the generated sample UI for real, without a GPU or
window: it instantiates `demo::gen::Demo`, calls the generated `build()` into a scene, lays the tree
out with Yoga (`LayoutEngine` + `apply_layout`), paints it through `paint_scene` and the
deterministic CPU canvas, dispatches synthetic pointer/text input, and compares three committed CPU
goldens at tolerance 0.

```bash
# CTest (registered from tests/unit because tests/integration is not in the root build yet).
ctest -R generated_ui --output-on-failure

# Run directly; --write regenerates the committed goldens deliberately.
./build/<preset>/tests/unit/generated_ui_tests <font.ttf> tests/golden/baseline/generated_ui
./build/<preset>/tests/unit/generated_ui_tests --write <font.ttf> tests/golden/baseline/generated_ui
```

What it proves today: the generated `Button` `PointerUp` binding increments the component's state
cell and the generated `apply_state()`/`update()` path repaints it (`Count: 1`) marking
`Paint|Render` but never `Layout`; the event route is the standard W3C capture/target/bubble order;
two runs are byte-identical; and the generated `TextInput` is editable end to end through
`tessera_text_edit` - the scripted typing/caret/selection sequence is published as
`PaintData::decoration`, and the `editing.png` golden shows the text, the selection highlight and
the caret (the demo asserts the caret/selection rects stay inside the content box, the caret sits at
the right edge of a half-open selection, and deleting the selection collapses it). Goldens:
`before.png`, `after.png`, `editing.png`; every frame paints with `FontPaintTextMetrics` so
decoration geometry matches the glyph renderer.

What it also documents as codegen gaps: controlled `value`/`onChange` wiring for `TextInput` (the
demo publishes the edit buffer itself; the generated binding still takes the generic `Event`) and
`automationId` emission (the demo resolves nodes by element kind). The precise controlled-input
contract the compiler must emit (event record fields/units, generated member signature, per-edit vs
commit timing, `PaintData`/state mapping) is in
[`compiler.md` §11](../design/compiler.md#11-c-codegen-first-slice-implemented).

## 5. Binding manifest

`generated/bindings.json` maps each binding id to its component, file, and protected region.
Renames go through a migration step; the merger never guesses. Keep the manifest in version
control so code review can see binding moves.

## 6. Editing rules

- Do not edit generated code outside protected regions.
- Do not rename a binding id by hand; use the migration/generator path.
- Do not add business logic to generated stubs outside a region.
- Keep developer regions small and focused; the region ids and placement are part of the contract between generated and developer code.
- Do not rely on generated line numbers; the file can change on regeneration.
- If a binding disappears, resolve the warning explicitly (restore the binding or remove the
  developer code yourself).

## 7. Review checklist

- [ ] No edits outside protected regions.
- [ ] `tessera generate --check` passes.
- [ ] Binding ids are unique and the manifest is updated.
- [ ] Merger idempotency test passes.
- [ ] Generated code is formatted with the pinned clang-format.
- [ ] Tests cover the new behavior; no wall clock/network/system fonts.
- [ ] Docs updated for new config/behavior/ADR.

## 8. Contributing to the framework

- Read [`AGENTS.md`](../../AGENTS.md) and the relevant ADR (see [decisions/README.md](../../decisions/README.md)) before changing architecture.
- Every subsystem gets a design note in `docs/design/` and, if contentious, an ADR.
- New dependencies require `docs/specs/dependencies.md` and `THIRD_PARTY_NOTICES.md` entries.
- Keep files under the 300/500-line soft/hard limits ([ADR-015](../../decisions/ADR-015-code-style-build-cache.md), code style and build cache).
- Run format/lint/tests on Windows and Linux (AGENTS.md definition of done requires both).
- Do not add a blocking wait on the UI thread; use async/cancellation ([ADR-021](../../decisions/ADR-021-async-runtime.md), async runtime).
- Do not leak OS/GPU types into the UI layer ([ADR-020](../../decisions/ADR-020-window-resize-and-lifecycle.md), window resize and lifecycle; [ADR-023](../../decisions/ADR-023-os-event-normalization-and-foldables.md), OS event normalization).
